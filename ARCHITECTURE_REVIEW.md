# Architecture Review
Generated: 2026-10-06T16:26:12.229Z
Score: 62/100

## Summary
Small, well-documented React/Vite mini-app with a sensible split (pages, components, lib, data) and a pure, testable calculator core. However, there is a serious type-contract drift (contract.ts vs types.ts), a copy-pasted haptic/try-catch helper in four places, a broken/duplicated import-alias style, and a large amount of unused scaffold template code (components, utils, storage helpers) that bloats the codebase.

## Issues
### Critical
- [consistency] src/lib/contract.ts declares types with the same names as src/lib/types.ts (SalaryEntry, CpiData, PairRow, AppResult, AmountInputResult, SaveResult, LoadResult) but with incompatible shapes. For example, CpiData is a `{[year]: number}` map in contract.ts but `{source, asOf, rates[]}` in types.ts. PairRow and AppResult differ completely, and SaveResult has an `error` field in one but not the other. The 'auto-generated, do not modify' contract is stale and contradicts the real domain model, so anyone importing from it gets wrong types. Function signatures also disagree: renderShareCardFn returns Blob while renderShareCard returns Promise<Blob>, and saveShareImageFn returns Promise<SaveResult> while saveShareImage returns an outcome string. — Files: src/lib/contract.ts, src/lib/types.ts, src/lib/shareCard.ts / Fix: Delete contract.ts or regenerate it from the real implementation. Make src/lib/types.ts the single source of truth for domain types, and re-export from it if a contract file is still needed.

### Warnings
- [duplication] The 'fire haptic feedback, guard against WebView throw' snippet (`try { Promise.resolve(generateHapticFeedback({type})).catch(() => {}) } catch {}`) is copy-pasted in at least five places: BottomCTA.fireHaptic, FloatingTabBar (inline), ShareCardButton.fireHaptic, Home.haptic, and Result.tickWeak. The same try/catch-and-swallow SDK pattern also recurs in AdSlot, review, share, and analytics. — Files: src/components/BottomCTA.tsx, src/components/FloatingTabBar.tsx, src/components/ShareCardButton.tsx, src/pages/Home.tsx, src/pages/Result.tsx / Fix: Extract a single `lib/haptics.ts` (export `haptic(type)`) and import it everywhere. Optionally add a generic `safeCall` helper in lib for SDK access, alongside analytics' fireAndForget.
- [dead_code] Many scaffold components and helpers appear unused in the app: FloatingTabBar, MiniBar, Sparkline, CountUp, TossPurchase, TossRewardAd (and its reward-ad.css), the EmptyState/LoadingState parts that aren't used, the SummaryHero `ai` prop, and `cn`/`formatCurrency` in utils.ts. Also unused: storage.ts `setItem`/`getItem`/`removeItem` outside review.ts, share.ts `shareApp`, `DWELL_MS`/`LogFields` exports, and `getLatestCpiYear` (used only by Result, if at all). Unused components also pull the SDK (IAP, rewarded ads) into the bundle graph if imported anywhere. — Files: src/components/FloatingTabBar.tsx, src/components/MiniBar.tsx, src/components/Sparkline.tsx, src/components/CountUp.tsx, src/components/TossPurchase.tsx, src/components/TossRewardAd.tsx, src/lib/utils.ts, src/lib/share.ts / Fix: Remove components and helpers that the app doesn't use, or move them into a clearly labeled template/vendor folder excluded from the app bundle. Run a tool such as knip or ts-prune to confirm.
- [consistency] Import styles are inconsistent. Most files use the `@/` alias, but App.tsx, main.tsx, Amount, CountUp, PageShell, SummaryHero, ScreenScaffold, and review.ts use relative paths (`../lib/utils`, `./storage`, `./pages/Home`). RaiseBars/ShareCardButton/Home use `@/`. The same module is reached by both styles. — Files: src/components/Amount.tsx, src/components/CountUp.tsx, src/components/PageShell.tsx, src/lib/review.ts, src/App.tsx / Fix: Pick one convention (prefer the `@/` alias for cross-directory imports, relative only for same-folder siblings) and enforce it with an ESLint rule.
- [consistency] Inconsistent error-handling and storage patterns. entriesStore wraps localStorage in try/catch and returns result objects, while lib/storage.ts's setItem/removeItem throw (and getItem swallows errors). review.ts has to compensate with a try around setItem. Result.tsx's compute() calls entriesStore.clear() as a side effect inside what looks like a pure read function, and silently destroys user data on a parse failure. Components use hard-coded colour tokens in two forms: `var(--adaptiveGrey600)` strings versus `adaptive.grey400` from @toss/tds-colors. — Files: src/lib/storage.ts, src/lib/entriesStore.ts, src/lib/review.ts, src/pages/Result.tsx, src/components/RaiseBars.tsx / Fix: Make storage.ts safe for all operations (or have entriesStore use it), and make Result's compute() side-effect free, with the clear moved to an explicit handler. Standardise on one colour-token approach.

### Suggestions
- [duplication] Amount and CountUp render the same inline-block/nowrap/tabular-nums span wrapper and Paragraph.Text with formatNumber + unit. They also each redefine the `Typography` type alias. Card's and PageShell's module-load 'safe pick from namespace' guards are also near-identical in intent. — Files: src/components/Amount.tsx, src/components/CountUp.tsx, src/components/Card.tsx, src/components/PageShell.tsx / Fix: Have CountUp render `<Amount value={display} .../>` and share the Typography type from one place. Move the safe-namespace-pick helper into a shared util.
- [duplication] Domain constants and validation are duplicated across modules: MAX_MEMO_LENGTH = 10 is defined in both Home.tsx and entriesStore.ts. MIN_ENTRIES = 2 is in Result.tsx while calculator.ts hardcodes `entries.length < 2`. Range limits live in calculator.ts, while Home has a RANGE_HELP string that hardcodes the same 1~100,000 values. `formatNumber`/`won` formatting is also redefined locally in Result. — Files: src/pages/Home.tsx, src/lib/entriesStore.ts, src/pages/Result.tsx, src/lib/calculator.ts / Fix: Export shared constants (MIN_ENTRIES, MAX_MEMO_LENGTH, MIN/MAX_AMOUNT_MAN) from calculator.ts or a `lib/constants.ts`, and derive RANGE_HELP from them.
- [naming] Mixed naming conventions. File names mix PascalCase components with non-matching names (`BottomCTA.tsx` exports `SubmitFooter`, `StateView.tsx` exports `EmptyState`/`LoadingState`). `__TdsGallery.tsx` and `__resetForTest` use underscore prefixes. contract.ts uses `getSlotYearsFn` style type names with a lowercase first letter. Comments and identifiers mix Korean and English. — Files: src/components/BottomCTA.tsx, src/components/StateView.tsx, src/lib/contract.ts, src/pages/__TdsGallery.tsx / Fix: Rename files to match their primary export (SubmitFooter.tsx, or export a BottomCTA). Use PascalCase for types and keep one convention for dev-only files.
- [structure] Domain/UI boundaries are blurred. `data/cpi.ts` contains logic (getSlotYears, getLatestCpiYear) and imports types from lib. entriesStore imports the data module and calculator for validation, and shareCard.ts imports from calculator (formatSignedPct), so the formatting helper sits inside the calculation module. `ShareCardButton` is a feature component sitting next to generic scaffold components in components/, as is `RaiseBars`, which takes domain types. Also, `reward-ad.css` is imported from the component, while the rest uses inline styles. — Files: src/data/cpi.ts, src/lib/calculator.ts, src/components/ShareCardButton.tsx, src/components/RaiseBars.tsx, src/components/TossRewardAd.tsx / Fix: Split components/ into `ui/` (generic scaffold) and `features/` (domain-aware) folders. Move formatSignedPct to a `lib/format.ts`, and keep data/ purely static with helper functions in lib/.
- [circular_dep] No true import cycles were found among the visible files. The dependency chain is acyclic (pages → components → lib → data/types). Note however that data/cpi.ts → lib/types, entriesStore → data/cpi + calculator, and shareCard → calculator keep lib and data tightly coupled, so a future import of entriesStore from calculator would create a cycle. — Files: src/data/cpi.ts, src/lib/entriesStore.ts, src/lib/calculator.ts / Fix: Keep calculator.ts dependency-free apart from types, and add an import-cycle lint check such as eslint-plugin-import `no-cycle` or madge in CI.
